学习路线 · 第 4 步

参与协作专题

你一个人用 Git 是存档，一群人用 Git 才是协作。用多张图和循序渐进的小练习，学会 clone、push、pull 和 Pull Request 这套团队流程。

先建立概念

协作的起点：你的仓库，和团队共用的远程仓库

当你提交到本地，别人还看不到。想让别人看到，就得把本地提交推送（push）到远程；想看别人的，就又拉取（pull）回来。这一页按“第一次进来 → 推送 → 拉取 → 团队流程”的顺序带你走通全程。

页面地图

这一页怎么带你把协作跑熟

01

第一次进来：clone

git clone 把远程的代码和历史完整复制到你的电脑，并记住远程叫 origin。

02

把成果送出去：push

git push 把本地新提交推送到远程，队友才能看到你的成果。

03

把更新收进来：pull

git pull 把别人的新提交拿到本地并合并，大家始终同步。

04

团队标准：Pull Request

先分支、后推送、再请求合并，主干始终保持可发布，改动先隔离在分支上。

第 1 步 · 第一次进来

git clone：一键把整个远程仓库搬回家

不用手动建仓库、设远程，一条命令全搞定

拿到项目地址后运行 git clone 仓库地址，Git 会复制全部代码 + 完整提交历史，并自动把远程记住为 origin。

这意味着你马上拥有和团队一致的完整副本，可以直接开始开发，不需要再手动配置远程。

第 2 步 · 把成果送出去

git push：提交到本地，只是成功的一半

push 之前，你的成果只有你自己看得见

你在本地 commit 了，但远程还是旧的。运行 git push，本地新提交才会被送上云端。

推完之后，想告诉队友“可以看了”，一句话就够了：“我推送了，拉一下。”

提醒：commit 在本地，改起来很自由；push 之后历史要谨慎改写（见前面的 amend 说明），推出去的东西要负责任。

第 3 步 · 把更新收进来

git pull：一条命令同步大家的进展

开发前先 pull，能少踩很多坑

队友可能早已 push 了新提交。git pull 会先 git fetch（把远程更新下载下来），再 git merge（合进你当前分支）。

开头养成习惯：每次开始写代码前先 pull 一下，避免在你已经落后的旧代码上继续改，这也是减少冲突最有效的一招。

如果两边恰好改了同一个文件的同一处，Git 会停下让你解决冲突——别慌，按分支专题里讲的方法处理即可。

第 4 步 · 团队标准

Pull Request：改动先在分支上隔离，审查通过再合进主干

为什么主干要“干净”

主干（main）始终保留可发布的版本。所有新改动先在分支上做，确认没问观才合回来。

我的流程清单

git pull 同步 → git switch -c 分支 → 提交 → git push → 在平台上开 PR → 等审查合并。

PR 的意义

PR 是“请队友看一下我的改动”。它把代码审查、讨论和合并放在一处，保证质量也方便追责。

动手练习

15 分钟模拟一次团队协作

练习任务

  • 把任意已有仓库推到远程，或用一份 git clone 的地址复制一份到新文件夹。
  • 改动一个文件并 git commit，运行 git push 推送到远程。
  • 换到另一份克隆里，运行 git pull，观察它拿到你的新提交。
  • 两个副本各自修改同一处并先后 push，体验 pull 时的冲突处理。
  • 在平台上开一个分支并提交 Pull Request，走一遍审查、合并、删除分支。

记忆口诀

先 clone 进门，通了就 push 出成果，开工前 pull 收更新；主干保持干净，改动走分支加 PR。
